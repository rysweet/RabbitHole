# Modernization corpus manifest

The modernization corpus manifest is the checked-in, text-only evidence record
for representative Alice archive coverage:

```text
docs/reference/modernization-corpus-manifest.json
```

It lets the modernization scorecard report corpus evidence without checking in
large Alice project, world, class, image, audio, video, or other media payloads.
It is intentionally independent of Git LFS.

This manifest is representative evidence only. It is not full historical archive
coverage and must not be described as a replacement for the original Alice
corpus or a complete compatibility archive.

## Usage

Use the manifest when a branch needs to show that generated Alice archive fixture
coverage exists for modernization review, but the repository must remain
lightweight and LFS-independent.

The manifest records the generated fixture shapes protected by deterministic
tests. The `path` values name expected fixture shapes, not checked-in binary
files. A path ending in `.a3p`, `.a3w`, or `.a3c` in this manifest does not mean
that archive payload exists in the repository.

The scorecard generator reads the manifest during scorecard generation:

```sh
python3 scripts/generate-modernization-scorecard.py \
  --output docs/reference/modernization-scorecard.md
```

When the manifest is valid, the generated scorecard reports the
LFS-independent corpus manifest as present and includes the representative entry
count. When the manifest is absent, the scorecard still generates but reports
corpus evidence as missing. When the manifest exists but is malformed, scorecard
generation fails closed.

## Manifest contract

The manifest is JSON with schema version `1`.

```json
{
  "schemaVersion": 1,
  "coverageStatement": "Representative corpus evidence only; this is not full historical archive coverage.",
  "entries": [
    {
      "id": "generated-project-xml-fallback",
      "path": "generated-fixtures/project-io/generated-project-xml-fallback.a3p",
      "description": "Representative editable project archive covering Alice XML fallback read/write behavior without checking in the binary archive.",
      "generatedFixtureExpectations": [
        "Generated by HistoricalArchiveRoundTripCharacterizationTest using deterministic project fixtures.",
        "Archive entries include version.txt, manifest.json, programType.xml, resources.xml, and a resources/<name> payload when the fixture includes a generated resource.",
        "Round-trip read/write assertions preserve the generated program type, scene-camera metadata, and generated resource identity/content fields."
      ],
      "journeys": [
        "project-io-corpus",
        "open-load-save"
      ],
      "notes": "The path names the expected generated fixture shape; the .a3p payload is intentionally not checked in."
    }
  ]
}
```

### Top-level fields

| Field | Required | Contract |
| --- | --- | --- |
| `schemaVersion` | Yes | Must be integer `1`. |
| `coverageStatement` | Yes | Must plainly state that the manifest is representative evidence only and is not full historical archive coverage. |
| `entries` | Yes | Must be a non-empty array of representative generated fixture entries. |

Unknown top-level fields are rejected. This keeps the manifest small and avoids
silent schema drift.

### Entry fields

| Field | Required | Contract |
| --- | --- | --- |
| `id` | Yes | Stable, non-empty entry identifier. Use lower-case words separated by hyphens. |
| `path` | Yes | Non-empty repository-relative expected generated fixture path. Must not be absolute, `.`, or contain parent traversal. |
| `description` | Yes | Non-empty plain-language explanation of the represented Alice archive behavior. |
| `generatedFixtureExpectations` | Yes | Non-empty array of non-empty strings that describe the generated fixture expectations protected by tests. |
| `journeys` | No | Optional non-empty array of non-empty modernization journey identifiers connected to the entry. |
| `notes` | No | Optional string for scope notes, exclusions, or known boundaries. When used, keep it concrete enough for review. |

Unknown entry fields are rejected. The manifest should describe evidence, not
become a second test framework.

## Representative entries

The checked-in manifest covers the representative generated fixture shapes that
matter to the current modernization scorecard.

| Entry | Expected fixture path | Archive shape represented |
| --- | --- | --- |
| `generated-project-xml-fallback` | `generated-fixtures/project-io/generated-project-xml-fallback.a3p` | Editable project archive behavior: manifest metadata, XML fallback project payloads, resource entries, and read/write round-trip assertions. |
| `generated-player-manifest` | `generated-fixtures/project-io/generated-player-manifest.a3w` | Exported player archive behavior: JSON manifest metadata, Tweedle source entries, resource references, and current decode boundaries. |
| `generated-type-xml-fallback` | `generated-fixtures/project-io/generated-type-xml-fallback.a3c` | Generated type archive behavior: XML fallback type payloads, resource metadata, and resource-expression rebinding. |

These paths are intentionally documentation metadata. Do not create matching
checked-in `.a3p`, `.a3w`, or `.a3c` files unless a separate reviewed corpus
payload policy explicitly allows them.

The manifest treats `.a3w` player exports as excluded Alice archive payloads for
corpus evidence even though repository attributes do not currently mark every
Alice archive extension the same way. The exclusion is part of this manifest
policy and review contract, not a signal that the generator should inspect local
payload files.

## Validation behavior

The scorecard generator validates the manifest before rendering corpus evidence.

| Condition | Result |
| --- | --- |
| Manifest file is absent | Scorecard generation succeeds and reports corpus evidence as missing. |
| Manifest file is valid | Scorecard generation succeeds and reports the manifest as present with the representative entry count. |
| Manifest file is present but malformed | Scorecard generation fails with a concise validation error. |

Validation rejects:

1. invalid JSON or a non-object top-level value;
2. missing or unsupported `schemaVersion`;
3. missing or weak `coverageStatement` wording;
4. missing, empty, or non-array `entries`;
5. unknown top-level or entry fields;
6. empty entry identifiers, descriptions, paths, expectations, or journeys;
7. absolute paths, `.` paths, or paths with parent traversal;
8. missing or empty `generatedFixtureExpectations`;
9. non-string `notes` values when `notes` is present.

Review policy also rejects entries that imply Alice archive payloads are checked
in instead of generated. That wording check is intentionally described as review
policy here rather than generator-enforced schema validation, so the documented
contract does not overstate what the current scorecard generator can prove.

Failing closed is intentional. A stale or vague manifest would make the
scorecard overstate corpus confidence.

## Scorecard integration

The generated scorecard includes a `Corpus gaps` section. That section reports
three facts:

1. where the scorecard looked for the checked-in manifest;
2. whether the LFS-independent manifest was present and valid;
3. that Git LFS payloads are not required for scorecard generation.

The scorecard renders only summary status and the number of entries in the
checked-in manifest. It does not dump the full manifest, open the expected
fixture paths, fetch Git LFS objects, or inspect local Alice archive payloads.

## API and automation contract

The stable automation interface is the scorecard generator CLI:

```sh
python3 scripts/generate-modernization-scorecard.py [--root PATH] [--output PATH]
```

There is no stable Python package API for the corpus manifest validator.
Repository tests may import generator internals for characterization, but
external automation should treat the manifest as repository-owned input and the
generated Markdown scorecard as output.

Automation may read `docs/reference/modernization-corpus-manifest.json` directly
when it needs the entry metadata, but it must preserve the same semantics:

1. treat paths as generated fixture shape references;
2. do not require the referenced `.a3p`, `.a3w`, or `.a3c` files to exist;
3. do not hydrate Git LFS or fetch external archives;
4. do not treat the manifest as full historical archive coverage.

## Configuration

The manifest has no separate configuration file. Its configuration is the
checked-in JSON document at:

```text
docs/reference/modernization-corpus-manifest.json
```

The scorecard generator reads the manifest relative to the inspected repository
root. With `--root`, the manifest is resolved under that root:

```sh
python3 scripts/generate-modernization-scorecard.py \
  --root ../alice-modernization-worktree
```

Local automation that wraps the Python command should preserve the repository
Node memory preference when Node is involved:

```sh
export NODE_OPTIONS=--max-old-space-size=32768
```

The corpus manifest and scorecard generator themselves are Python and JSON
artifacts. They do not depend on Node, Git LFS, network access, or external schema
packages.

## Examples

### Add evidence for a new generated fixture shape

Add a new entry when a generated fixture test protects a new representative
archive boundary.

```json
{
  "id": "generated-project-with-audio-resource",
  "path": "generated-fixtures/project-io/generated-project-with-audio-resource.a3p",
  "description": "Representative editable project archive covering generated audio resource metadata and readback without checking in the binary archive.",
  "generatedFixtureExpectations": [
    "Generated by HistoricalArchiveRoundTripCharacterizationTest using deterministic in-memory resource data.",
    "Archive entries include version.txt, manifest.json, programType.xml, resources.xml, and a resources/<name> payload for the generated audio resource.",
    "Readback assertions preserve generated resource identity, content type, original name, and bytes."
  ],
  "journeys": [
    "project-io-corpus"
  ],
  "notes": "The .a3p path describes the expected generated fixture shape only; no Alice binary payload is checked in."
}
```

After updating the manifest, regenerate the scorecard and review the `Corpus
gaps` section:

```sh
python3 scripts/generate-modernization-scorecard.py \
  --output docs/reference/modernization-scorecard.md
```

### Preview corpus evidence from another worktree

```sh
python3 scripts/generate-modernization-scorecard.py \
  --root ../alice-modernization-worktree
```

The preview reports corpus evidence for the inspected worktree, not necessarily
for the current shell directory.

### Keep binary payloads out of the change

Before handing off a manifest-only change, verify that the diff contains text
documentation, JSON metadata, tests, or scorecard output only. Do not include
files with these payload extensions:

```text
.a3p
.a3w
.a3c
```

Do not include generated media files, large fixture directories, or Git LFS
pointer files for corpus evidence. `.a3w` is included in this exclusion by
manifest policy even if local Git attributes do not currently classify it as
binary.
