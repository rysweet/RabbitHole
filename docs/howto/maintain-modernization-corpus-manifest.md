# Maintain the modernization corpus manifest

Use this guide when a branch adds, removes, or changes representative generated
Alice archive fixture coverage and the modernization scorecard needs to show the
updated corpus evidence.

The corpus manifest is representative evidence only. It is not full historical
archive coverage. Do not use this workflow to check in `.a3p`, `.a3w`, `.a3c`,
image, audio, video, or other Alice archive payloads.

## Prerequisites

Work from the repository root. The manifest lives at:

```text
docs/reference/modernization-corpus-manifest.json
```

Read the durable schema and scorecard contract first:

```text
docs/reference/modernization-corpus-manifest.md
docs/reference/modernization-scorecard-generator.md
```

If the branch also changes project archive characterization tests, initialize the
Tweedle grammar submodule before broad Maven validation:

```sh
git submodule update --init tweedle-lang
test -d tweedle-lang/Grammar
```

## Decide whether the manifest should change

Update the manifest only when the representative generated fixture set changes.

| Change | Manifest action |
| --- | --- |
| A generated `.a3p`, `.a3w`, or `.a3c` fixture shape is newly protected by tests | Add an entry. |
| A generated fixture shape is no longer protected or no longer representative | Remove or revise the entry. |
| Test expectations change for an existing representative fixture | Update `generatedFixtureExpectations`. |
| Only implementation details change and the observable generated fixture contract is unchanged | Leave the manifest unchanged. |
| A historical binary archive is available locally | Do not add it to the manifest as checked-in evidence. |

The manifest should stay small. It is an evidence index, not a full test catalog.

## Add or revise an entry

Each entry needs a stable identifier, an expected generated fixture path, a plain
description, and generated-fixture expectations.

Use this shape:

```json
{
  "id": "generated-project-xml-fallback",
  "path": "generated-fixtures/project-io/generated-project-xml-fallback.a3p",
  "description": "Representative editable project archive covering Alice XML fallback read/write behavior without checking in the binary archive.",
  "generatedFixtureExpectations": [
    "Generated by HistoricalArchiveRoundTripCharacterizationTest using deterministic project fixtures.",
    "Archive entries include version.txt, manifest.json, programType.xml, resources.xml, and a resources/<name> payload when the fixture includes a generated resource.",
    "Round-trip read/write assertions preserve the generated program type, scene-camera metadata, and generated resource identity/content fields."
  ],
  "journeys": [
    "project-io-corpus",
    "open-load-save"
  ],
  "notes": "The path names the expected generated fixture shape; the .a3p payload is intentionally not checked in."
}
```

Keep entry wording concrete:

1. name the production seam or test suite that generates the fixture;
2. name the archive entries or metadata that define the behavior;
3. name the readback or round-trip expectations;
4. state explicitly that the Alice archive payload is not checked in when the path ends
   in `.a3p`, `.a3w`, or `.a3c`.

## Preserve representative-only scope

The top-level `coverageStatement` must remain explicit:

```json
"coverageStatement": "Representative corpus evidence only; this is not full historical archive coverage."
```

Do not soften this language. The scorecard relies on the manifest being honest
about its limits.

Avoid phrases such as:

```text
complete corpus coverage
full Alice archive compatibility
all historical projects
the historical archive corpus is covered
```

Use phrases such as:

```text
representative generated fixture evidence
expected generated fixture shape
not full historical archive coverage
binary payload intentionally not checked in
```

## Regenerate the scorecard

After editing the manifest, refresh the checked-in scorecard:

```sh
python3 scripts/generate-modernization-scorecard.py \
  --output docs/reference/modernization-scorecard.md
```

The `Corpus gaps` section should report:

```text
LFS-independent corpus manifest | Present | Found <n> representative checked-in corpus manifest entries.
Git LFS payloads | Not required | The scorecard does not fetch or inspect large binary project files.
```

In that row, "checked-in corpus manifest entries" means entries in the checked-in
JSON manifest. It does not mean checked-in `.a3p`, `.a3w`, or `.a3c` payload
files.

If generation fails, fix the manifest validation error instead of weakening the
scorecard generator.

## Validate focused behavior

For manifest and scorecard changes, run the focused Python scorecard tests:

```sh
NODE_OPTIONS=--max-old-space-size=32768 \
python3 -m unittest tests.test_modernization_scorecard
```

For a handoff that changes repository documentation or scorecard behavior, run
Python discovery:

```sh
NODE_OPTIONS=--max-old-space-size=32768 \
python3 -m unittest discover -s tests
```

If the branch also changes generated archive characterization tests, run the
focused Maven suite:

```sh
mvn -pl core/story-api-migration -am \
  -DfailIfNoTests=false \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=org.lgna.project.io.HistoricalArchiveRoundTripCharacterizationTest \
  test
```

## Review the diff

For an ordinary manifest entry update, the expected diff is usually:

```text
docs/reference/modernization-corpus-manifest.json
docs/reference/modernization-scorecard.md
```

When the schema, validation behavior, scorecard behavior, or contributor
workflow changes, the diff may also include:

```text
docs/reference/modernization-corpus-manifest.md
docs/reference/modernization-scorecard-generator.md
docs/index.md
tests/test_modernization_scorecard.py
```

It must not include:

```text
*.a3p
*.a3w
*.a3c
generated-fixtures/
media fixture payloads
Git LFS object additions
```

The change is ready for review when the manifest stays representative, the
scorecard shows corpus evidence accurately, and no binary corpus payloads are
part of the commit.
