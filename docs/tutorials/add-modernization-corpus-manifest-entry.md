# Tutorial: Add a modernization corpus manifest entry

This tutorial walks through documenting a new representative generated Alice
archive fixture in the modernization corpus manifest.

The example adds evidence for a generated editable project archive that contains
an audio resource. The archive path is metadata only; the `.a3p` file is not
checked in.

## Goal

Add a manifest entry that tells the scorecard:

```text
A deterministic generated .a3p fixture shape is covered by characterization
tests. The fixture protects audio resource archive metadata and readback
behavior. The binary .a3p payload remains generated at test runtime and is not
stored in Git or Git LFS.
```

This is representative evidence only. It is not full historical archive
coverage.

## 1. Open the manifest

Edit:

```text
docs/reference/modernization-corpus-manifest.json
```

Keep the top-level statement explicit:

```json
"coverageStatement": "Representative corpus evidence only; this is not full historical archive coverage."
```

## 2. Choose an entry ID

Use a stable, lower-case, hyphen-separated identifier:

```json
"id": "generated-project-audio-resource"
```

The ID should describe the representative fixture shape, not an implementation
helper method.

## 3. Choose the expected fixture path

Use a repository-relative generated fixture path:

```json
"path": "generated-fixtures/project-io/generated-project-audio-resource.a3p"
```

The path describes the expected generated archive shape. Do not create this
`.a3p` file in the repository.

Invalid paths include:

```text
/tmp/generated-project-audio-resource.a3p
../generated-project-audio-resource.a3p
.
```

## 4. Write the description

Describe the represented behavior in one sentence:

```json
"description": "Representative editable project archive covering generated audio resource metadata and readback without checking in the binary archive."
```

Good descriptions name the archive type, the behavior, and the binary exclusion.

## 5. Add generated-fixture expectations

List the expectations protected by the generated fixture test:

```json
"generatedFixtureExpectations": [
  "Generated by HistoricalArchiveRoundTripCharacterizationTest using deterministic in-memory audio resource data.",
  "Archive entries include version.txt, manifest.json, programType.xml, resources.xml, and a resources/<name> payload for the generated audio resource.",
  "Readback assertions preserve generated resource identity, content type, original name, and bytes."
]
```

Each expectation should be observable from the generated archive or production
readback behavior. Avoid vague claims such as "covers audio" or "works with old
projects."

## 6. Connect the entry to modernization journeys

Use `journeys` when the entry maps to a known review or QA journey:

```json
"journeys": [
  "project-io-corpus",
  "open-load-save"
]
```

Keep journey names short and stable. Do not use local branch names, issue titles,
or person-specific labels.

## 7. Add an explicit note

Use `notes` to prevent reviewers from mistaking the path for a checked-in
payload. The generator validates that `notes` is a string when present; reviewers
enforce whether the wording is clear enough:

```json
"notes": "The path names the expected generated fixture shape; the .a3p payload is intentionally not checked in."
```

## 8. Review the completed entry

The finished entry looks like this:

```json
{
  "id": "generated-project-audio-resource",
  "path": "generated-fixtures/project-io/generated-project-audio-resource.a3p",
  "description": "Representative editable project archive covering generated audio resource metadata and readback without checking in the binary archive.",
  "generatedFixtureExpectations": [
    "Generated by HistoricalArchiveRoundTripCharacterizationTest using deterministic in-memory audio resource data.",
    "Archive entries include version.txt, manifest.json, programType.xml, resources.xml, and a resources/<name> payload for the generated audio resource.",
    "Readback assertions preserve generated resource identity, content type, original name, and bytes."
  ],
  "journeys": [
    "project-io-corpus",
    "open-load-save"
  ],
  "notes": "The path names the expected generated fixture shape; the .a3p payload is intentionally not checked in."
}
```

## 9. Regenerate the scorecard

Refresh the generated scorecard:

```sh
python3 scripts/generate-modernization-scorecard.py \
  --output docs/reference/modernization-scorecard.md
```

Confirm the `Corpus gaps` section reports the updated representative entry
count.

## 10. Run focused validation

Run the scorecard tests:

```sh
NODE_OPTIONS=--max-old-space-size=32768 \
python3 -m unittest tests.test_modernization_scorecard
```

Run Python discovery before handoff:

```sh
NODE_OPTIONS=--max-old-space-size=32768 \
python3 -m unittest discover -s tests
```

If the branch also adds or changes the generated archive characterization test,
run the focused Maven suite:

```sh
mvn -pl core/story-api-migration -am \
  -DfailIfNoTests=false \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=org.lgna.project.io.HistoricalArchiveRoundTripCharacterizationTest \
  test
```

## 11. Check for accidental payloads

Before review, make sure the change did not add Alice archive fixture payloads:

```text
No .a3p files
No .a3w files
No .a3c files
No generated media files
No Git LFS object additions
```

`.a3w` player exports are excluded by modernization corpus policy even if a local
Git attribute rule does not classify that extension as binary.

The manifest entry is complete when it documents the generated fixture shape,
keeps representative-only scope clear, updates the scorecard evidence, and
leaves Alice archive payloads out of the repository.
